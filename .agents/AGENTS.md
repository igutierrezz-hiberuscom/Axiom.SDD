# Axiom Bootstrap Orchestrator Mode

This repository is currently developed using a lightweight SDD workflow.

Do not apply the future full Axiom product lifecycle unless explicitly requested.

## Repository Roles

### `Axiom.SDD` (this repository)
Use this repository for implementation and tooling work, including:
- core code and adapters
- scripts and commands
- prompts and workflows
- repository-specific technical documentation

### `Axiom.Spec` (sibling repository)
Use `Axiom.Spec` as the canonical specification repository. It contains:
- `AGENTS.md`
- `specs/` (canonical specs `00_Resumen_Ejecutivo.md` through `08_Glosario.md` and per-increment/bug specs)
- `context/` (technical-context knowledge base)

### `Axiom` (optional)
Product code: `packages/*` and `apps/*`.

## Multi-Repository Workspace Guidance

When a parent workspace includes `Axiom.SDD`, `Axiom.Spec`, and optional `Axiom`, agents must:
1. Identify which repository each requested change belongs to.
2. Refine canonical increment or bug specs in `Axiom.Spec` first.
3. Implement code changes in `Axiom.SDD` / `Axiom`.
4. Update `Axiom.Spec/specs/` and `Axiom.Spec/context/` only with stable, consolidated knowledge.

## Bootstrap Lifecycle (Increments and Bugs)

For increments and bugs, follow this lifecycle:
1. Understand the request.
2. Locate or create the increment or bug spec in `Axiom.Spec`.
3. Refine the spec with goal, scope, non-goals, and acceptance criteria.
4. Ask critical questions only when needed.
5. Produce a short internal implementation plan.
6. Implement focused changes in `Axiom.SDD` / `Axiom`.
7. Validate using available tests, build commands, lint commands, or manual inspection.
8. Review the result against the original intent and acceptance criteria.
9. Close or leave pending with explicit reason.
10. Integrate stable knowledge into `Axiom.Spec`.

## General Rules

- Prefer simple, useful, validated changes.
- Do not create speculative architecture.
- Do not duplicate canonical specification content into `Axiom.SDD`.
- Keep canonical product and behavior knowledge in `Axiom.Spec`.
- Use `Axiom.SDD` for implementation and repository-specific technical documentation.
- If a validation command exists, run it.
- If no validation command exists, state that clearly and perform best-effort validation.
- Do not modify unrelated files.
- Do not persist a plan by default.
- Persist a plan only when the task is large, risky, cross-repo, or likely to span multiple sessions.

## Explicit Bootstrap Limits

Do not introduce the following unless explicitly requested:
- mandatory indexes
- complex metadata systems
- enterprise lifecycle folders
- work item integrations (Azure DevOps, Jira)
- MCP abstractions as mandatory dependencies
- Workbench logic
- heavy multi-agent orchestration frameworks
- deep autogenerated folder hierarchies
- scripts that do not exist yet

## Validation Discovery Order

Check for validation commands in this order:
1. `README` files
2. package scripts
3. task runners
4. test configurations
5. build configurations
6. available scripts

If no validation command is found, use this exact statement:
`No validation command was found. Performed best-effort validation by inspecting changed files and checking consistency against the requested behavior.`
