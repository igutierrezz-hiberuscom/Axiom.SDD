# Axiom Bootstrap Orchestrator Mode

This repository is currently developed using a lightweight SDD workflow.

Do not apply the future full Axiom product lifecycle unless explicitly requested.

## Repository Roles

### `Axiom.SDD` (this repository)

Use this repository for implementation and tooling work, including:

- core code and adapters
- scripts and commands
- prompts and workflows
- repository-specific technical documentation

### `Axiom.Spec` (sibling repository)

Use `Axiom.Spec` as the canonical specification repository. It should contain, or evolve toward, this structure:

- `specs/` (numbered canonical specs, with `specs/increments/` and `specs/bugs/`)
- `context/`
- `bugs/` and `increments/` (existing top-level artifact roots; canonical workspace specs are under `specs/`)
- `technical-context/` (derived technical-context indexes)
- `plans/`
- `templates/`
- `prompts/`
- `decisions/`

Canonical product and behavior knowledge must be consolidated there.

### `Axiom` (optional)

Treat as optional or future consumer space. Do not assume stable logic unless files explicitly indicate it.

## Multi-Repository Workspace Guidance

When a parent workspace includes `Axiom.SDD`, `Axiom.Spec`, and optional `Axiom`, agents must:

1. Identify which repository each requested change belongs to.
2. Refine canonical increment or bug specs in `Axiom.Spec` first.
3. Implement code changes in `Axiom.SDD`.
4. Update the owning files under `Axiom.Spec/specs/`, `Axiom.Spec/context/`, or `Axiom.Spec/decisions/` only with stable, consolidated knowledge.

## Bootstrap Lifecycle (Increments and Bugs)

For increments and bugs, follow this lifecycle:

1. Understand the request.
2. Locate or create the increment or bug spec in `Axiom.Spec`.
3. Refine the spec with goal, scope, non-goals, and acceptance criteria.
4. Ask critical questions only when needed.
5. Produce a short internal implementation plan.
6. Implement focused changes in `Axiom.SDD`.
7. Validate using available tests, build commands, lint commands, or manual inspection.
8. Review the result against the original intent and acceptance criteria.
9. Close or leave pending with explicit reason.
10. Integrate stable knowledge into the owning file under `Axiom.Spec/`.

## General Rules

- Prefer simple, useful, validated changes.
- Do not create speculative architecture.
- Do not duplicate canonical specification content into `Axiom.SDD`.
- Keep canonical product and behavior knowledge in `Axiom.Spec`.
- Use `Axiom.SDD` for implementation and repository-specific technical documentation.
- If a validation command exists, run it.
- If no validation command exists, state that clearly and perform best-effort validation.
- Do not modify unrelated files.
- Do not persist a plan by default.
- Persist a plan only when the task is large, risky, cross-repo, or likely to span multiple sessions.

## Explicit Bootstrap Limits

Do not introduce the following unless explicitly requested:

- mandatory indexes
- complex metadata systems
- enterprise lifecycle folders
- work item integrations (Azure DevOps, Jira)
- MCP abstractions as mandatory dependencies
- Workbench logic
- heavy multi-agent orchestration frameworks
- deep autogenerated folder hierarchies
- scripts that do not exist yet

If something appears useful but belongs to the future enterprise product lifecycle, document it as a future consideration and do not implement it now.

## Increment Rules

- Create or update increment specs in `Axiom.Spec/specs/increments/`.
- If that path does not exist, use the equivalent increment folder in the spec repository structure.
- Keep increment specs concise and actionable.
- Do not mark an increment as `closed` unless closure rules are fully satisfied.

## Bug Rules

- Create or update bug specs in `Axiom.Spec/specs/bugs/`.
- If that path does not exist, use the equivalent bug folder in the spec repository structure.
- Clarify expected behavior before implementation.
- Do not mark a bug as `closed` unless closure rules are fully satisfied.

## Validation Rules

Validation discovery order:

1. `README` files
2. package scripts
3. task runners
4. test configurations
5. build configurations
6. available scripts

If no validation command is found, use this exact statement:

`No validation command was found. Performed best-effort validation by inspecting changed files and checking consistency against the requested behavior.`

## Documentation Rules

When closing an increment or bug:

1. Update its own file first.
2. Update the owning canonical file under `Axiom.Spec/` only with stable knowledge.
3. Do not copy the full implementation history into a canonical specification.
4. Keep canonical specifications clean, consolidated, and reusable.
5. If no stable knowledge needs integration, state that explicitly in the increment or bug file.

## Closure Rules

An increment or bug can be marked `closed` only if all are true:

- Goal or expected behavior is clear.
- Acceptance criteria exist.
- Changes were implemented, or no-code rationale is explicit.
- Available validation was executed.
- Review against intent and acceptance criteria was done.
- Stable knowledge was integrated into the owning `Axiom.Spec` file when applicable.
- Result was documented clearly.

If any item is missing, set:

`Status: pending`

and explain why.
